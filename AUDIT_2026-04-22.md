## The big question

**Is Lovable + Supabase + TS-with-as-any sustainable?** Honest: at ~60% complete and pre-revenue you're fine, but the productivity ceiling is in sight. Three forces are colliding:

1. **Lovable writes plausible-looking code that skips the type system.** Every `as any` and every ad-hoc `.insert({...})` shape is a future 3am bug. You've already lost a 12-hour debug to this.
2. **Supabase migrations are append-only but schema drift is silent.** When types.ts falls behind, Lovable's next generation gets the wrong schema and writes MORE drift. The three broken migrations (C1) are proof — they've been in the tree for days and nothing flagged them.
3. **No CI.** Every commit is trusted to "compile in Lovable's sandbox". There's no `tsc --noEmit` gate, no `supabase db lint`, no migration dry-run.

Verdict: keep Lovable for UI iteration, but put three rails under it:
1. **`tsc --noEmit` must pass** on every push. Start with `"strict": false` and `// @ts-expect-error` escape hatches if needed, but the build must succeed.
2. **`supabase gen types` runs in CI** and fails the build if `types.ts` is stale vs prod.
3. **A one-page schema map** — markdown doc that lists every `jobs`/`properties`/`client_properties`/`quote_requests` column and which code path reads/writes it. Lovable can consume this in every prompt and stop inventing columns.

With those three rails, Lovable stays fast and safe. Without them, the next 12-hour debug is 3-4 weeks away.
